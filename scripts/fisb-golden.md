# The tg30 golden output (`skycue/tests/fixtures/fisb/tg30.golden.jsonl`)

## What it is

`tg30.golden.jsonl` is the output of

    skycue-fisb --json --ref-date 2020-10-30 skycue/tests/fixtures/fisb/tg30.978

(1772 lines, 1,729,462 bytes): every FIS-B store event, in the order the store
emits it. It holds 1088 `fisb_text`, 562 `fisb_twgo`, 5 `fisb_radar`,
28 `fisb_raster` and 89 `fisb_expired` records. The test `fisb_cli`
(`skycue/tests/test_fisb_cli.sh`) compares a fresh run with it byte for byte.
Every time in the file, `received` included, comes from the input's `t=`
stamps, so two runs are byte-identical. `--ref-date` does not matter for tg30, because every line has
a `t=`.

**The golden is generated by skycue-fisb itself.** It is not a conversion of
fisb-decode's output. Instead, every record in it was checked against
fisb-decode's own decoding of the same file, as described below. fisb-decode
prints every decoded message, repeats included. skycue-fisb prints what its
store publishes: a record once when it is new or changed, and a mosaic each
time it is published. Rewriting fisb-decode's stream into our store events
would mean writing our store again in Python. So the comparison checks
containment instead, family by family, in both directions where that makes
sense.

## Running fisb-decode without MongoDB

fisb-decode (https://github.com/rand-projects/fisb-decode, BSD-2-Clause Plus
Patent) was taken from the same snapshot as `tg30.978` (cloned 2026-11-01;
the cross-check below was last re-run on 2026-11-02 from a fresh clone at
commit `c3d3b047` of 2022-09-05, the repository's latest commit on both
dates). Levels 0-2 are pure Python 3.
Python 3.9 was used, with no third-party modules. Only level 0 imports
`pymongo`, and only when `CALCULATE_RSR` is on (the reception-success-rate
statistics). Level 3 and the harvester need MongoDB, but the check below does
not use them.

```sh
FD=/path/to/fisb-decode                  # the clone
W=$(mktemp -d)
cp -r "$FD/fisb" "$W/"                    # work on a copy of the package
sed -i 's/^CALCULATE_RSR = True/CALCULATE_RSR = False/' "$W/fisb/level0/level0Config.py"
cd "$W"                                   # the levels write LEVELn.ERR into the current directory
export PYTHONPATH="$W"
python3 fisb/level0/level0.py < skycue/tests/fixtures/fisb/tg30.978 > l0.jsonl   # path to this repo's fixture
python3 fisb/level1/level1.py < l0.jsonl > l1.jsonl
python3 fisb/level2/level2.py < l1.jsonl > l2.jsonl
```

This is `bin/decode` without level 3. It takes under a second; no `.ERR` file
is written and stderr stays empty. `l0.jsonl` and `l1.jsonl` have 963 lines
each. `l2.jsonl` has 9961: 7892 IMAGE, 913 METAR, 272 NOTAM, 256 G_AIRMET,
185 AIRMET, 121 TAF, 79/72/65 WINDS_24/12/06_HR, 46 SERVICE_STATUS, 35 SUA,
4 SIGMET, 4 PIREP and 17 CRL records. The service status and CRL records have
no counterpart in our store.

## The check

```sh
python3 -I scripts/fisb-golden-check.py "$W/l2.jsonl" skycue/tests/fixtures/fisb/tg30.golden.jsonl --examples 4
```

The script first checks the golden against the store's own TWGO rules, and
`--golden-only` runs just that part, without fisb-decode:

```sh
python3 -I scripts/fisb-golden-check.py --golden-only skycue/tests/fixtures/fisb/tg30.golden.jsonl
```

no `fisb_twgo` record whose report year is not its data clock's year (562
checked); no record drawn as active before its start: `pending` is true
exactly when `start` is after the record's time (562 checked, 132 pending);
and no AIRMET, SIGMET or CWA record whose start (else its text header's
`ddhhmm`) is more than 12 h before or more than 6 h after its time (80
checked).

The script (its docstring has the details) fails on the first golden record
that fisb-decode does not confirm, and on the first distinct fisb-decode
METAR, TAF or TWGO report that the golden never publishes. Result (the
fisb-decode cross-check as last run in full, on the golden before the final
review's regeneration; see "Final review regeneration" below for what changed
since):

| What | Matched |
|---|---|
| METAR: station, observation time, full text | 748 (all 748 distinct FD METARs covered) |
| TAF: station, issue time, full text | 121 (all 121 covered) |
| PIREP: time, full text | 2 exact, plus 1 adjudicated (below) |
| Winds: station, period, `issued` = FD `issued_time`, `valid` = FD `valid_time`, data line | 216 |
| TWGO text (AIRMET, SIGMET, G-AIRMET has none) | 84 exact |

### Adjudicated differences

Each of these was traced to fisb-decode's source and is allowed by the
script. Each is counted separately.

1. **CONUS empty blocks, 381.** We give them level 1; FD gives them 0. This
   follows design ruling §10.6 and reference §5.4.
2. **NOTAM text, 265.** FD's `msg8_16_17.py` drops the
   `NOTAM-D KEYE.10/028 010100Z ` header and the spaces before line breaks.
   We keep the text as sent. The rest of the text is identical.
3. **Single-altitude shapes, 175.** When a shape has one altitude,
   `utilities.py` in FD writes `[alt, ref, 0, ref]`, so the 0 is a filler.
   We set low = high = alt. The top altitude agrees.
4. **PIREP station, 1.** For `PIREP KMEM 300840Z MEM UA ...` our station is
   `KMEM`, the first token after the type. FD's is `MEM`, from the report's
   own location field. The time and text are identical.
5. **FD's `BAD_MESSAGES`, 0 records (as of 2026-11-02).** `msg11_12_15.py`
   in FD has a hard-coded list of "stuck" SIGMETs that it ignores on
   purpose. The script still allows a golden record whose text is on that
   list, but none is left: SIGMETs 12-20-7489 and 12-20-7676 (the July 2020
   text `WST KMKC 062057 CONVECTIVE SIGMET 99C`, still re-broadcast in this
   October capture, start 2020-07-06) were 4 records here until the store
   began rejecting AIRMET/SIGMET/CWA reports whose start is more than 12 h
   old (`store.stale_start`, design §10.2 amended 2026-11-02). The 2019
   report 19-7540 that this entry covered before that is rejected by the
   year check (`wrong_year`).
6. **TFR keep-alives 0-230, 0-852, 0-7764, 3.** FD prints a `renew-only`
   NOTAM for each. The full text of these reports never arrives in tg30, so
   the store creates nothing (§10.2).

### Expiry (not checked by the script)

fisb-decode expires a NOTAM-D at its text's end of validity and a NOTAM-TFR
70 min after its last reception (a keep-alive renews it). The store ends
every NOTAM, AIRMET, SIGMET, G-AIRMET and CWA at the earlier of its latest
end time and 70 min after its last reception (design §10.3, amended at the
final review), so for TFRs it now agrees with fisb-decode. An earlier version
of this file listed TFRs 0-5116 and 0-229 as "expiry differs from
fisb-decode" because the store kept their text's end (2021-09-01 and
2021-10-29): that was a bug in the store, not a representational difference.
A NOTAM-D that stops being broadcast leaves the store before FD's
`expiration_time`.

## Final review regeneration (2026-11-02)

The golden was regenerated after the final review's store fixes. Against the
previous golden (1749 lines): the `fisb_text`, `fisb_radar` and
`fisb_raster` records are identical, and the `fisb_expired` records name the
same keys at the same times. In `fisb_twgo` (539 -> 566 records, 464 -> 462
reports):

- every record gains `kind: "twgo"` and `pending`;
- the 4 records of SIGMETs 19-7540 and 19-7086 (report year 2019 in 2020
  data) are gone: the store rejects another year's report
  (`store.wrong_year`). 19-7540 was adjudication 5 (FD's `BAD_MESSAGES`);
  19-7086 is now allowed in the reverse check as "FD TWGO report of another
  year than the data: rejected by the store";
- 31 G-AIRMET (14) records are added: reports published `pending: true`
  (start 09:00Z, after their reception) published again `pending: false`
  when the clock reaches their start. Their shapes are those of the same
  report's earlier record. 132 records are pending in all; the previous
  golden drew 134 such records as active;
- `expires` changed for 327 of the 462 reports: NOTAMs, AIRMETs, SIGMETs,
  G-AIRMETs and CWAs now end at the earlier of their end and 70 min after
  their last reception.

`--golden-only` passes on the new golden, and the fisb-decode cross-check
was re-run on it on 2026-11-02 (levels 0-2 regenerated: 963, 963 and 9961
lines, no `.ERR` file). Result `OK`; the table above holds these numbers.
Against the previous run only the shape counts moved: 216 exact and 175
single-altitude (the 31 republished G-AIRMET records bring their shapes
again, 11 exact and 20 single-altitude). The "another year" allowance was
not needed, because no FD TWGO report of 2019 is checked for coverage.
Adjudication 5 is still used, by the two 2020 stuck SIGMETs named there,
not by 19-7540.

## Stuck-SIGMET regeneration (2026-11-02)

The golden was regenerated after the store began rejecting stale-on-arrival
AIRMET, SIGMET and CWA reports (design §10.2, amended 2026-11-02). Against
the previous golden (1776 lines) exactly 4 lines are removed and none added
or changed: the text and the text-plus-graphics records of SIGMETs
12-20-7489 and 12-20-7676 (`CONVECTIVE SIGMET 99C`, start 2020-07-06T20:55Z,
graphics end 2021-01-01). `fisb_twgo` goes from 566 to 562 records and 462
to 460 reports; no `fisb_expired` record named them (they were still live at
the end of the capture). `skycue-fisb --summary` counts
`store.stale_start 6`: the receptions of their halves.

`--golden-only` passes (the previous golden now fails its new stale check
on 12-20-7489), and the fisb-decode cross-check was re-run on 2026-11-02
against the same level-2 output (9961 lines). Result `OK`; every matched
count in the table above is unchanged (they never counted the two stuck
SIGMETs), adjudication 5 is now unused (0), and the other allowed counts
are unchanged: 381, 265, 175, 3 and 1.

## Regenerating

After an intended change to the decoder, store or JSON writers:

```sh
skycue-fisb --json --ref-date 2020-10-30 skycue/tests/fixtures/fisb/tg30.978 \
  > skycue/tests/fixtures/fisb/tg30.golden.jsonl
python3 -I scripts/fisb-golden-check.py "$W/l2.jsonl" skycue/tests/fixtures/fisb/tg30.golden.jsonl
```

Then review the diff and adjudicate every new difference here.
